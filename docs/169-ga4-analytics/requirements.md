# 要件定義: GA4 によるユーザー価値到達のイベント計測（#169）

## Problem Statement

現在のアクセス解析は Cloudflare Web Analytics（#76）のみで、URL 単位の PV/UU しか観測できていない。
その結果、LibCheck の中核的な価値である

> 気になった本について、普段使う図書館で借りられるかを確認し、実際の予約行動につなげること

に、ユーザーがどこまで到達しているかが分からない。具体的には次が観測できていない。

- ISBN 読み取り → 検索結果表示 → 図書館の予約ページ遷移というファネルの通過率
- 収益化（Amazon アソシエイトリンク）への到達
- Google 検索からの流入ユーザーがその後どこまで進んだか（#155 SEO Epic の効果測定）

今回の目的は網羅的な分析基盤の構築ではなく、**最小限のイベント計測を確実に動かし、
現状のベースラインを取り始めること**である。実データを見て分析仮説が生まれた段階で、
必要なパラメータを追加できる構造にしておく。

## Requirements

### 機能要件

1. GA4（gtag.js）を本番環境で利用可能な構成で導入する。
2. 次の4イベントを計測する。ユーザー価値の指標と収益化の指標は混ぜず、別イベントで追う。

   | イベント | 意味 | 区分 |
   | --- | --- | --- |
   | `isbn_scan_success` | カメラで ISBN の読み取りに成功した | ファネル入口 |
   | `book_search_result_view` | 書籍情報と登録図書館の蔵書状況を確認できる状態になった | ファネル中間 |
   | `library_reservation_link_click` | 図書館の予約・蔵書検索サイトへのリンクをクリックした | **ユーザー価値（主要）** |
   | `amazon_affiliate_link_click` | Amazon アソシエイトリンクをクリックした | **収益化** |

3. `book_search_result_view` には次の数値パラメータを付与する。

   - `searched_library_count`: 検索対象となった図書館数
   - `holding_library_count`: 蔵書が見つかった図書館数
   - `available_library_count`: 現在貸出可能な図書館数

4. 測定 ID はコードへハードコードせず、環境変数で設定・管理する。
5. 開発者がローカルでイベントの発火を確認できる手段を用意する。

### 非機能要件

1. **重複送信をしない**: SPA の再レンダリング、React StrictMode の二重 effect、
   React Query の再取得（retry）によってイベントが複数回送信されないこと。
2. **既存の CSP を弱めない**: `script-src` に `'unsafe-inline'` / `'unsafe-eval'` を追加しないこと。
3. **プライバシー**: ISBN・書名・図書館名などの高カーディナリティな値、および個人を特定できる
   情報を GA4 のイベントパラメータとして送らないこと。
4. **既存機能への非破壊**: 計測の失敗・未設定・広告ブロックがアプリの動作に影響しないこと
   （計測は常に best-effort の副作用として扱う）。
5. **拡張余地**: 実データを見た後にパラメータ・イベントを追加できる構成にすること。

## Constraints

- **CSP**: `public/_headers` の CSP は `script-src 'unsafe-inline'` を許可しておらず、
  `security-headers.test.ts` がそれを regression テストで固定している。Google 公式の
  gtag.js スニペットはインライン `<script>` を含むため、そのままでは使用できない。
- **Cloudflare Pages のプレーン環境変数は `wrangler pages deploy` で消える**（既知の罠）。
  そのため測定 ID はビルド時インライン（GitHub Actions の env）で注入する。
- **GA4 は Cookie（`_ga` 等）を使用する**。既存のプライバシーポリシーは「Cookie は認証目的のみ」
  と記載しているため、更新が必要。
- **GA4 の debug_mode のデータも通常レポートに含まれる**。開発時の送信は既定で行わない。
- 既存の Cloudflare Web Analytics（#76）は撤去せず併用する。
- GA4 プロパティの作成・GitHub リポジトリ変数 `GA_MEASUREMENT_ID` の登録はリポジトリ所有者が行う。
- 大規模なリファクタリングは行わない。GA4 のための変更は最小限に留める。

## Acceptance Criteria

- [ ] 本番ビルドで GA4 が初期化され、測定 ID はビルド時の環境変数から注入される（ハードコードなし）。
- [ ] `isbn_scan_success` が、バーコードから ISBN を読み取れたときに 1 回だけ送信される。
- [ ] `book_search_result_view` が、検索結果（書籍情報＋蔵書状況）を確認できる状態になったときに
      ISBN あたり 1 回だけ送信され、3 つの数値パラメータを伴う。
- [ ] `library_reservation_link_click` が「予約する」リンクのクリックごとに 1 回送信される。
- [ ] `amazon_affiliate_link_click` が「Amazonで見る」リンクのクリックごとに 1 回送信される。
- [ ] 再レンダリング・再試行・StrictMode によって上記イベントが二重送信されない（テストで担保）。
- [ ] CSP に `'unsafe-inline'` を追加せずに gtag.js が読み込め、本番でコンソールに CSP 違反が出ない。
- [ ] 測定 ID 未設定時（ローカル既定）はネットワーク送信せず、コンソール出力のみで確認できる。
- [ ] プライバシーポリシーに GA4 と Cookie 利用が記載されている。
- [ ] 型チェック・テスト・ビルドが通る。

## User Stories

- **サービス運営者として**、ISBN を読み取ったユーザーのうち何割が予約リンクまで到達したかを知りたい。
  次に改善すべき箇所（読み取り精度か、結果画面の分かりやすさか、予約導線か）を決めるため。
- **サービス運営者として**、図書館予約への到達と Amazon への到達を区別して見たい。
  ユーザー価値と収益化はトレードオフになり得るため、片方の数字でもう片方を誤って判断したくない。
- **サービス運営者として**、SEO 施策（#155）で流入したユーザーがその後どこまで進んだかを知りたい。
  流入数だけでなく価値到達で施策を評価するため。
- **開発者として**、ローカル開発中にどのイベントがどんなパラメータで飛ぶかを確認したい。
  本番のデータを汚さずに実装の正しさを検証するため。
- **利用者として**、どんな情報が解析目的で外部送信されるかをプライバシーポリシーで確認したい。
